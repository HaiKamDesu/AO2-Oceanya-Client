## viewport lag

**Also called:** "viewport lag", "background loading slow", "character sprite freeze", "animated bg freezes when emote loads", "layer load freezes other layers", "static images lag", "KamLoremaster slower than GIF", "async loading", "sprite transparent for a few frames", "emote flashes transparent before loading", "sprite not frame perfect"

**Status:** Confirmed

**Layer-load freeze root cause:** all animated layers advance on ONE shared UI-thread `DispatcherTimer` at `DispatcherPriority.Render` (`Ao2AnimationPreview.cs` `BitmapFrameAnimationPlayer`/`GifAnimationPlayer` ~1873/2250), so ANY synchronous work on the UI thread during a render starves the timer and every animated layer (e.g. an animated background) freezes for those frames. Two dominant synchronous costs were removed (both in `AO2ViewportAssetResolver.cs`): (1) `TryGetImageSize` fully DECODED the background just to read its pixel dimensions for placement — replaced with header-only `TryReadImageHeaderSize` (`BitmapDecoder` metadata, `BitmapCacheOption.None`), falling back to full `LoadImage` only for formats WPF can't decode natively (WebP); (2) `ResolvePathCaseInsensitive`/`ResolveDirectoryCaseInsensitive` ran `Directory.EnumerateFiles`/`EnumerateDirectories` (a full directory scan of possibly-large character/asset folders) on EVERY wrong-extension probe — `ResolveImageStem` probes 6 `ImageExtensions` × every `Globals.BaseFolder` mount per layer per render — even though on Windows `File.Exists` already matches case-insensitively so the scan can never find anything new. Guarded by `FilesystemIsCaseSensitive` (`!RuntimeInformation.IsOSPlatform(OSPlatform.Windows)`): on Windows the enumeration fallback is skipped (behavior-identical, `File.Exists` already case-insensitive); kept on Linux where paths are case-sensitive. Remaining per-render UI-thread cost is cheap `File.Exists`/`GetLastWriteTimeUtc` stats + in-memory-cached decodes. Do NOT reintroduce a full decode for size measurement or an unconditional directory-scan fallback on the render path. **Render timing instrumentation:** `AO2ViewportControl.RenderScene` times each phase via a local `Lap()` stopwatch and, when total ≥ `RenderTimingLogThresholdMs` (default 4.0ms; lower to capture more), logs `[RENDER-TIMING] total=… | theme=… bg=… charResolve=… charSet=… desk=… overlays=… chat=… tail=… | phase=… bg=… char=… emote=…` at Info under `LogCategory.Viewport` (Debug Console `[VPT]`, exportable). Use it to find which phase dominates a hitch on the user's real machine/assets before optimizing further. BG/desk: `SetPlacedAnimatedImage` in `AO2ViewportControl.xaml.cs` — async `Task.Run` + `Dispatcher.BeginInvoke` when not cached. Character/pair: `SetCharacterAnimatedImageAsync` — same pattern with an `onPlayerReady` callback that chains into the pre-animation → speaking flow. Static PNG/JPG character and placed image loads must not decode on the UI thread; cache hits use `Ao2AnimationPreview.TryLoadCachedStaticPreviewImage(...)`, cache misses decode through `AO2ViewportAssetResolver.LoadImage(...)` on a worker. Animated GIF/WebP can stream first frame through `TryStreamGifFrames`/`TryStreamWebPFrames`. Pre-animation timing is driven by `handlePreAnimationPlayer` in `RenderPreAnimationThenSpeaking`; callback fires synchronously on cache hit or via dispatcher after async decode. Animation cache check via `Ao2AnimationPreview.IsAnimationCached`. **Transparent-flash fix:** on the cache-MISS async paths in `SetCharacterAnimatedImageAsync` (static and animated), do NOT set `image.Source = null` / `Visibility = Collapsed` before the background decode — that blanked the sprite for a few frames. `StopAnimation` freezes the last frame in `image.Source` WITHOUT clearing it, so the previously-shown frame stays on screen until the new image is decoded and swapped in (cache hits are already synchronous/frame-perfect). `RenderMessage` never calls `ClearScene` (that is detach-only at ~346/424/605), and `SetCharacterAnimatedImageAsync` is the only per-message writer of `CharacterImage.Source`, so keeping the old frame guarantees no transparency between emotes. Do not reintroduce the pre-clear or a synchronous UI-thread decode (would re-cause lag).

## shout cut off

**Also called:** "shout cut off", "long objection", "custom shout duration", "Lyria objection", "shout first-use lag", "custom shout falls back to default visual"

**Status:** Confirmed

AO2 reference: `AO2-Client/src/courtroom.cpp` `handle_objection` starts `ui_vp_objection` and continues only on `finishedPlayback`; `AO2-Client/src/animationlayer.cpp` caps each frame at `shout_max_time` 1500 ms, not total duration; `AO2-Client/src/animationloader.cpp` uses `QtConcurrent::run` to populate frames in background. Oceanya path: `AO2ViewportControl.ShowShoutOverlay` / `RenderShoutOverlay` / `SetShoutAnimatedImageAsync` / `ScheduleShoutContinuation`; GIF/WebP shouts stream first frame immediately via `Ao2AnimationPreview.TryStreamGifFrames` / `TryStreamWebPFrames`, then continue on `PlaybackFinished`. Shout visual lookup is `AO2ViewportAssetResolver.ResolveShoutOverlayImage(...)`; viewport first resolves `CharacterFolder` from packet character/showname, then uses the folder name for `characters/<folder>/<holdit|objection|takethat>_bubble.*` so showname packets do not miss custom visuals. Multi-mount parity: each shout candidate VPath searches every `Globals.BaseFolders` mount before theme/default fallback, matching AO2 `get_real_path`; regression `Test_AO2ViewportAssetResolver_ShoutSearchesAllMountsBeforeThemeFallback`. Asset duration helper `AO2ViewportAssetResolver.GetShoutDuration(...)`; capped frame sum helper `Ao2AnimationPreview.TryEstimateAnimationDuration(path, maximumFrameDuration, out duration)`. Static/undecodable fallback remains 724 ms. Regression: `UnitTests/StructureTests.cs` `Test_AO2ViewportAssetResolver_ShoutDurationUsesFullAnimationWithAo2FrameCap` and `Test_AO2ViewportAssetResolver_ResolvesCharacterShoutOverlayFromResolvedShowname`.

## custom chatbox

**Also called:** "custom chatbox", "chatbox P5", "Open in file explorer chatbox", "character chat misc", "chat=default"

**Status:** Confirmed

`AO2ViewportAssetResolver.ResolveCharacterChatToken(...)` reads `[Options] chat`; missing/empty chat stays an empty AO2 misc token and must not become `misc/default`. Oceanya intentionally diverges from AO2 for `[Options] chat=default`: treat literal `default` like no override so the active theme default chatbox is used instead of `misc/default`. `AO2ChatPreviewResolver.Resolve(...)` reads selected `config.ini` `theme`/`subtheme`/`theme_scaling_factor` and resolves chatbox art/fonts/design/config through AO2 `get_asset_paths(...)` priority; custom art without custom `courtroom_design.ini`/`courtroom_fonts.ini` falls back through the active theme chain, not preferred-theme guesses or unrelated `misc/default` geometry. WPF message text keeps a 4 px document margin to match Qt placement. `AO2ChatPreviewResolver.ResolveChatboxDirectoryPath(...)` backs the viewport Chatbox context-menu explorer target. **Perf (message-display freeze):** `AO2ChatPreviewResolver.Resolve(...)` runs ~4× per viewport render (talking style, text reveal, `ChatPreview.RefreshPreview`, theme layout) and each call merges 3 INI files (`courtroom_fonts.ini`/`chat_config.ini`/`courtroom_design.ini`) across the whole theme+mount chain. This previously re-read and re-parsed every INI from disk on EVERY call (dozens of `File.ReadLines` parses per render on the UI thread) — a major per-message hitch. Now `GetParsedIniCached` caches parsed key/value entries per resolved file keyed by `LastWriteTimeUtc` (edited INIs still live-reload), and `ResolveFileCaseInsensitive`/`ResolveStemCaseInsensitive` skip the `Directory.EnumerateFiles` case-insensitive fallback on Windows (guarded by `FilesystemIsCaseSensitive`; `File.Exists` is already case-insensitive there) — that fallback was scanning theme dirs for every missed config candidate across the chain. **`[RENDER-TIMING]` on a real busy-room log showed `Resolve` was STILL the dominant per-message cost (~8-13ms each ×4/render = the bulk of the `chat`/`theme`/`charResolve` phases) even after the parse cache — because each call re-enumerated the theme+mount chain doing ~45-60 `File.Exists` syscalls.** So `Resolve` now caches the WHOLE computed `AO2ChatPreviewStyle` in `ResolvedStyleCache` keyed by `BuildResolveCacheKey` (token + hasShowname + preferViewportTheme + theme + subtheme + scaling + `Globals.BaseFolders` signature) and validated by the last-write-times of the exact files it merged (`resolveDeps`, collected in `LoadMergedConfig` + the chatbox image path). Repeated same-input resolves return the cached style after only re-stat-ing its few dependency files; a theme/mount/config-theme change misses via the key; an edited INI misses via write-time (live-reload preserved). Only mid-session ADDITION of a not-previously-existing higher-priority file is not auto-detected — `AO2ChatPreviewResolver.ClearCache()` (called from `AO2ViewportControl.ReloadThemeLayout`) covers that. Do NOT reintroduce uncached per-render INI parsing, unconditional directory scans, or per-call full re-enumeration on this path. **`Resolve` now returns a SHARED cached `AO2ChatPreviewStyle` instance — callers must treat it as read-only and NEVER mutate it.** `AO2ChatPreviewControl.ApplyDynamicShownameLayout` used to write `style.ChatboxImagePath = med/big variant` for wide shownames; with the cache that corrupted the shared style on later renders (showname "Loremaster" rendered as "Lorem..." with wrong position and a stale/mis-sized showname background). It now RETURNS the effective chatbox image path (base or med/big variant) which `RefreshPreview` passes to `ApplyChatboxImage`, leaving the cached style untouched. Tests: `UnitTests/StructureTests.cs` `Test_AO2ChatPreviewResolver_ResultCacheReflectsEditedConfig` (cache-hit reuse + write-time live-reload).

## background priority

**Also called:** "background priority", "mount path priority", "duplicate background name", "refresh bg softlock", "viewport falls back to wrong background", "missing background should be transparent"

**Status:** Confirmed

`AOBot-Testing/Structures/Background.cs`; `Background.RefreshCache()` and `TryUpsertBackgroundInCache()` preserve AO2 mount priority by keeping the first matching `Globals.BaseFolders` background name. Cache writes must use `GetDistinctBackgroundsForCache()` so aliases/direct paths cannot serialize duplicate `Background.Name` values and break snapshot restore. Viewport background image resolution lives in `OceanyaClient/Features/Viewport/AO2ViewportAssetResolver.ResolveBackgroundPlacement(...)`: AO2 parity fallback is only same-background `wit.*`; missing background folders or missing current-bg images must return null so WPF viewport background stays transparent, never cross-fallback to `background/default`. Tests: `UnitTests/StructureTests.cs` missing/default fallback and same-background wit fallback cases.

## multi mount asset mismatch

**Also called:** "multi mount asset mismatch", "random Pearl fallback", "character asset fallback differs from AO2", "asset resolution priority"

**Status:** Confirmed

AO2 VPath behavior: `AO2-Client/src/path_functions.cpp` checks every mount path for the current candidate before trying the next fallback candidate; character emote candidates are built in `AO2-Client/src/animationlayer.cpp` `loadCharacterEmote`. Oceanya parity lives in `OceanyaClient/Features/Viewport/AO2ViewportAssetResolver.cs`: character pre/dialog/post animations use `ResolveCharacterImageAsset(...)`; shout/sticker/WTCE/evidence/speedline overlays use `ResolveImageVfs(...)` so a high-mount fallback asset cannot beat a lower-mount exact candidate. Regression: `UnitTests/StructureTests.cs` `Test_AO2ViewportAssetResolver_DialogAnimationSearchesAllMountsBeforePlaceholder` and `Test_AO2ViewportAssetResolver_ShoutSearchesAllMountsBeforeThemeFallback`.

## AOHD viewport gap

**Also called:** "AOHD viewport gap", "wide theme background shifts left", "background gap after talking", "overlay breaks after talking", "show chatbox on top of viewport"

**Status:** Confirmed

`AO2ViewportControl.RenderScene` applies theme layout before resolving AO2 placement; do not run another `ApplyThemeLayout()` after `SetPlacedAnimatedImage` because `SetViewportLayerSize` resets placed BG/desk width to raw viewport size. `ChatboxOverlapsViewport` toggles must call `ReapplyScenePlacementAfterLayoutChange()` after layout. ## character looks too small

**Also called:** "character looks too small", "W first emote bigger in AO2", "character sprite scaling"

**Status:** Confirmed

`AO2ViewportControl.SetCharacterAnimatedImageAsync` + `ApplyHeightBasedCharacterGeometry`; AO2 reference `AO2-Client/src/animationlayer.cpp::calculateFrameGeometry` scales non-stretched character frames by viewport height and clips over-wide sprites instead of width-constraining them with Uniform.

## chatbox message scrolls

**Also called:** "chatbox message scrolls", "long message not visible", "chatbox text reveal scroll", "long message slows down", "viewport slows with each line", "text reveal lag on long messages"

**Status:** Confirmed

`AO2ChatPreviewControl.xaml` `MessageTextBox` (a read-only, `Focusable=False` `RichTextBox`) uses `ScrollViewer.VerticalScrollBarVisibility="Hidden"` (was `Disabled`); `ScrollMessageToCurrentTextEnd()` (called from `ApplyPreviewTextOnly` on each reveal tick) scrolls to end so long messages auto-scroll as text is revealed. **Long-message O(n²) fix:** `AO2ChatTextFormatter.EnumerateFormattedTextSegments` yields ONE segment per grapheme, and the text reveal calls `ApplyFormattedMessageText` once per typing tick with a growing prefix. Building a `Run`+`SolidColorBrush` per segment created ~n Runs and n brushes every tick (n ticks → O(n²) allocation + inline-tree build + FlowDocument layout), the "long message slows down with each line" report. Fix in `AO2ChatPreviewControl.ApplyFormattedMessageText`: coalesce consecutive same-color segments into a single `Run` and reuse frozen brushes from `frozenBrushCache` (output identical — adjacent same-brush Runs render the same as one merged Run). Also `ScrollMessageToCurrentTextEnd` dropped the two `CaretPosition = ContentEnd` assignments (each forced a full synchronous layout validation, done 2× sync + 2× deferred = 4 growing layouts/tick) — caret is never visible on a read-only/non-focusable box — leaving a single Render-priority deferred `ScrollToEnd()`. Do NOT reintroduce per-grapheme Runs or CaretPosition-based scrolling.

## music restarts when switching clients

**Also called:** "music restarts when switching clients", "song starts over when I change profile", "music dies on client switch", "per-pane music"

**Status:** Confirmed

Only reproduces in multi-internal-client mode. Each profile owns its own `AO2ViewportControl` and therefore its own `AO2ViewportAudioManager`. `AO2ViewportControl.OnIsVisibleChanged` called `audioManager.StopAll()` when a pane was hidden, and `OnMusicChanged` was gated on `ShouldPlayViewportAudio` (`renderAudioEnabled && IsVisible`), so a hidden pane both lost its music and DROPPED incoming `MC#` packets. Switching profile therefore killed the room's song, and the pane switched to had no music state at all - the next `MC#` replayed it from zero. Single-internal-client mode has one shared pane keyed on `singleInternalClient`, which is why it never reproduced there.

Music is a room-level stream, not a per-pane one, so the fix is mute-not-stop: `AO2ViewportAudioManager.IsMusicAudible` scales the music and ambient player volumes through `ScaleMusicVolume(...)` while leaving the streams running at their real position. `OnIsVisibleChanged` now calls `StopSfxAndBlips()` plus `IsMusicAudible = false` on hide (one-shot audio still stops), and `OnMusicChanged` gates on `renderAudioEnabled` alone while setting `IsMusicAudible = IsVisible`, so a hidden pane keeps its stream in sync silently and re-selecting the profile resumes mid-song. The picture-in-picture mirror sets `RenderAudioEnabled = false` and is unaffected. `MainWindow.mainMusicAudioManager` (used only while the viewport window is hidden) is a single shared manager and never had the problem.
